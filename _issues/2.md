# Add authentication and per-customer authorisation

## Summary

Only an authenticated customer may use the MiniBank AI features, and they may only see or move money on **their own** accounts. This must hold for both hosts (`MiniBank.Console` and `MiniBank.Api`) and must be enforced **below the hosts** so the model, tools, and workflow cannot bypass it.

Prompting the LLM “not to talk about other customers” is not authorisation. Putting `[Authorize]` only on `POST /chat` is not enough either: `AccountTools`, `CustomerTools`, `TransactionTools`, and `OperationTools` all call `Bank` today with no caller identity, so any authenticated session can still look up Jane Doe, sum the whole bank, or transfer from account 10001.

## Motivation

The assistant is a banking product. Today anyone who can reach the Console loop or `POST /chat` acts as every seeded customer at once (`Alice Example`, `John Smith`, `Jane Doe`). `GET /health` is fine as a public liveness check; every AI turn is not.

Defence in depth:

| Layer | What it must do |
|---|---|
| Host (Console / API) | Authenticate the user. Refuse AI features if there is no principal. |
| Workflow / tools | Carry that principal into every lookup and write. Do not trust the model to pick “the right” owner or account. |
| `Bank` (source of truth) | Load, mutate, and list accounts only when they belong to the current customer. |

Writes still go Intent → Approval → Transfer/Decline. The model still must not receive deposit/withdraw/transfer tools. Authorisation is extra: even `TransferExecutor` / `OperationTools` / `Bank.TransferAsync` must refuse a debit from an account the caller does not own.

## Scope

### Identity

- A **customer principal** is the unit of authorisation. Map it onto the existing `Account.Owner` string used by the seed data (for example `John Smith`).
- Seed three demo users that match the existing accounts: Alice Example, John Smith, Jane Doe.
- One login session = one customer. Do not support an “admin who can see everyone” role here.

### Mock auth server (replaceable)

Ship an **in-memory mock identity server** as the first authentication source. Console and API must authenticate against that component (issue a token / validate a token / resolve the customer principal). Do not check passwords inside `MapPost("/chat")` or the Console `while` loop.

Keep a **single replaceable seam** (one interface, one in-memory implementation) for “sign in and give me a principal”. A later issue can swap the implementation for a real identity/OAuth/OIDC server (Entra, IdentityServer, Keycloak, etc.) without rewriting `Bank` authorisation, tools, or workflow. Hosts should keep depending on the seam, not on the mock’s internals.

The mock may:

- Hold the three demo users in memory (or config bound into memory at startup).
- Issue a bearer token (or equivalent) after username/password (or a documented demo login).
- Validate that token and return the customer principal (`Owner` / subject).

It must **not** become a second banking layer. It only answers “who is this caller?”.

### Authentication (hosts)

**API**

- `POST /chat` requires a valid authenticated caller (token from the mock auth server). Unauthenticated requests return **401** and must not call `BankingWorkflow` or Ollama.
- `GET /health` stays anonymous.
- A small login endpoint that talks to the mock auth server is fine (for example `POST /login` → token). Do not add a SPA or browser OAuth redirect flow in this issue.
- Do not treat the k8s Envoy `x-api-key` as customer identity. That key is for the internal AI gateway, not MiniBank users.

**Console**

- Prompt for credentials (or equivalent) **before** the chat loop, then authenticate via the same mock auth seam the API uses. Failed or missing login never constructs a workflow turn.
- After login, every question runs as that customer until the process exits (or an explicit logout, if you add one).

Log the authenticated customer with a structured property (for example `{Customer}`), not the password.

### Authorisation (`Bank` and everything that calls it)

Introduce a current-customer context that `Bank` (or a thin wrapper composed in front of `Bank`) requires on every customer-facing call. Hosts set it at the composition root after authentication. Tools and `TransferExecutor` must not accept a raw “act as any owner” `Bank`.

Enforce at least:

| Operation | Rule |
|---|---|
| `FindAccountAsync` / balance / history / deposits on one account | Allowed only if that account’s `Owner` is the current customer. Otherwise behave as **not found** (do not leak that the account exists or who owns it). |
| `GetAccountsByOwnerAsync` / owner totals / deposit counts / `find_accounts_by_owner` | Allowed only when the requested owner **is** the current customer (after the same name resolution you already use). Other names return empty / not found, never another customer’s balances. |
| `GetAllAccountsAsync` / `GetTotalValueAsync` / `get_highest_balance_account` | Must **not** expose the whole bank to a customer session. Scope to the current customer’s accounts, or refuse the operation. A customer must not learn Jane’s £5,000 total or Alice’s account number. |
| `DepositAsync` / `WithdrawAsync` | Allowed only on the current customer’s accounts. |
| `TransferAsync` | The **source** account must belong to the current customer. A transfer **to** someone else’s account is allowed (paying them). Debiting another customer’s account is not. |

Do **not** implement this only by filtering tool *descriptions* or relying on Intent Agent classification. If the model calls `get_balance` with Jane’s `20001` while logged in as John Smith, `Bank` must deny it.

Keep hosts thin: no per-account if-statements in `MapPost("/chat")`. The API authenticates, binds the principal, and calls `BankingWorkflow` as today.

### Tests

- Add **non-Ollama** tests that pin authorisation on `Bank` (and/or the tools) with the existing seed-style accounts: John cannot read Jane’s balance or debit 20001; John can read 10001/10002; transfer from 10001 to 20001 is allowed; transfer from 20001 to 10001 is not when the principal is John.
- API: unauthenticated `POST /chat` is 401; health is 200 without credentials. Prefer these without spinning Ollama (mock or short-circuit is fine if the host still uses `BankingWorkflow` for authenticated calls).
- Do **not** add or run Ollama-backed tests unless a follow-up explicitly asks.

### Docs

Update the README (how to run): how to log in to Console, how to call `POST /chat` with credentials, and that users only see their own accounts. Keep the existing example questions, but state which customer they belong to (for example John Smith → accounts 10001 / 10002).

## Out of scope

- Wiring a **real** identity/OAuth/OIDC provider (Entra ID, Auth0, IdentityServer, Keycloak). The in-memory mock plus a replaceable seam is the whole auth-server story for this issue.
- Customer self-registration, password reset, MFA, refresh-token rotation, JWKS/discovery documents.
- Admin / bank-teller roles that can see all accounts.
- Persisting users in Postgres (in-memory demo users are enough).
- Changing Intent → Approval → Transfer/Decline, or giving the model write tools.
- Using the k8s gateway API key as MiniBank customer auth.
- Re-enabling CI Ollama test jobs.
- New HTTP resources for accounts, balances, or transfers (those stay inside the workflow / `Bank`).

## Acceptance criteria

- [ ] Unauthenticated Console and API callers cannot run an AI / workflow turn.
- [ ] `GET /health` remains callable without login.
- [ ] After login as John Smith, lookups and history succeed only for 10001 and 10002; Jane Doe (20001) and Alice Example (1234567890) are not readable or debitable.
- [ ] John can transfer **from** 10001 **to** 20001 (credit someone else). John cannot transfer **from** 20001.
- [ ] Bank-wide questions (`get_total_value`, `get_highest_balance_account`) do not reveal other customers’ money or account numbers.
- [ ] Authorisation is enforced in `Bank` (or a single wrapper used by all tools and `OperationTools`), not only in ASP.NET filters or Console if-statements.
- [ ] Seeded demo users match the existing three customers.
- [ ] Both hosts authenticate through an in-memory mock auth server behind a single replaceable interface (not host-local password ifs).
- [ ] Non-Ollama tests cover the deny/allow matrix above, plus mock login success/failure (invalid credentials, missing token → 401).
- [ ] README documents login (mock users, how to get a token, Console prompt) and the per-customer rule for both hosts.

## Notes for implementers

- Composition today: hosts `new` `Bank`, tools, and `BankingWorkflow.Create(...)`. After this issue, the `Bank` (or wrapper) those tools receive must already be bound to the authenticated customer — or every `Bank` method must take a required principal. Do not thread “current user” through Minimal API endpoints as a second banking layer.
- Put the mock auth server next to other infrastructure (for example under `MiniBank.AI` or a small dedicated project), not duplicated in Console and API. Hosts only compose it. The only extra interface this issue should add is this replaceable identity seam (one implementation now: in-memory).
- `OwnerResolver` currently matches unique first names across **all** accounts. Under a customer principal it must not resolve “Jane” to Jane Doe’s accounts when John is logged in.
- Failed authorisation should look like the existing `AccountNotFoundException` path (or empty lists) so the API still does not leak stack traces or “this account belongs to Jane”.
- Default `IWriteApprover` remains `AutoApprover`. Approval is not a substitute for “is this my account?”.
- Verify with `dotnet restore MiniBank.AI.slnx` and `dotnet build MiniBank.AI.slnx --configuration Release`.
