# Add a thin Minimal API host alongside the Console client

## Summary

Add a new ASP.NET Core Minimal API project that is a second client of the existing MiniBank assistant. It should be a thin HTTP layer over `BankingWorkflow` — the same entry point the Console uses — with the same Serilog logging and OpenTelemetry tracing the Console already has.

The API must not grow its own agents, tools, or banking rules. Lookups still go through read-only tools; deposits, withdrawals, and transfers still run only after the workflow approval step.

## Motivation

`MiniBank.Console` is the only host today. It builds a generic host, wires Serilog and `AddMiniBankTracing`, seeds an in-memory bank, and chats through `BankingWorkflow.RunDetailedAsync`. An HTTP client is needed so other UIs or callers can hit the same workflow without going through the interactive console loop.

## Scope

### New project: `MiniBank.Api`

- Target `net10.0`, nullable enabled, implicit usings disabled (match the rest of the solution).
- Add it to `MiniBank.AI.slnx`.
- Project reference `MiniBank.AI` only (same as Console). Do not reference Domain / Repositories / Services unless Console already needs a type that is not re-exported — keep composition in the host the same way Console does.
- `dotnet run --project MiniBank.Api` should start Kestrel and serve the API.

### Thin Minimal API surface

Keep the HTTP surface small. Suggested contract (adjust names if a clearer convention fits):

- `POST /chat` (or `/ask`)
  - Request: `{ "question": "What's the balance of account 10001?" }`
  - Response: `{ "output": "...", "executorIds": ["IntentAgent", "QueryExecutor"] }`
  - Map 1:1 from `WorkflowRunResult`.
- Reject empty / whitespace questions with `400`.
- On workflow failure, log the exception (same as Console) and return `500` with a short error payload — do not leak stack traces to the client.
- Honour `CancellationToken` on the workflow call.

Optional but useful while staying thin:

- `GET /health` that returns `200` without calling Ollama.

Do **not** add REST resources for accounts, balances, deposits, or transfers. Those stay inside the workflow / `Bank` service.

### Host composition (mirror Console)

`MiniBank.Console/Program.cs` is the template:

1. `WebApplication.CreateBuilder` (instead of `Host.CreateApplicationBuilder`).
2. Serilog from configuration, then `builder.Logging.ClearProviders()` + `AddSerilog`.
3. `builder.Services.AddMiniBankTracing(builder.Configuration, "MiniBank.Api")` so traces are distinguishable from `MiniBank.Console`.
4. Seed the same in-memory bank as Console (Alice Example, John Smith, Jane Doe, same balances).
5. Construct `BankingWorkflow` with `AccountTools`, `CustomerTools`, `TransactionTools`, `OperationTools`, and the host `ILoggerFactory`.
6. Default `IWriteApprover` remains `AutoApprover` (workflow default). Do not invent a new approval path.
7. `Log.CloseAndFlushAsync()` on shutdown.

Copy Console’s seed + in-memory repository for now rather than extracting a shared host library, unless a tiny shared helper is clearly worth it. Prefer duplication of a few dozen lines over a new abstraction.

### Logging and instrumentation (must match Console)

`appsettings.json` should follow `MiniBank.Console/appsettings.json`:

- **Serilog**
  - Console sink, Literate ANSI theme, same output template.
  - Default Information; `Microsoft` and `System` Warning; `Microsoft.Extensions.AI` Debug.
  - `Enrich: FromLogContext`.
- **Tracing**
  - `"Tracing": { "Enabled": true, "OtlpEndpoint": "http://localhost:4317" }`.
  - Same OTLP gRPC export via existing `AddMiniBankTracing`.
  - Service name **`MiniBank.Api`**.
  - Tracing still off when `"Enabled": false`.

Expected telemetry (already produced by `MiniBank.AI`, not reimplemented in the API):

- `MiniBank.Agent` — `agent.run`, `agent.llm.chat`
- `MiniBank.Tools` — `tools.execute`
- Microsoft Agent Framework / Extensions.AI sources
- HTTP client calls to Ollama

Log the inbound question at Information (Console already logs `Sending question to MiniBank workflow: {Question}`).

### Out of scope

- Auth / API keys
- Persistence (`PostgresAccountRepository`)
- Swagger-heavy documentation beyond what Minimal APIs give for free (OpenAPI is fine if it stays one-liner)
- Frontend / SPA
- Changing workflow, tools, or approval behaviour
- Re-enabling CI test jobs
- Shared “host bootstrap” project unless the duplication is painful in review

## Acceptance criteria

- [ ] `MiniBank.Api` is in the solution and builds with the rest of CI (`dotnet build MiniBank.AI.slnx`).
- [ ] A single chat endpoint accepts a question and returns the workflow answer plus executor path.
- [ ] Writes still cannot be invoked by the model; they still go Intent → Approval → Transfer/Decline.
- [ ] Serilog configuration matches Console.
- [ ] `AddMiniBankTracing(..., "MiniBank.Api")` is registered; OTLP endpoint and enable flag come from `appsettings.json`.
- [ ] Same seed data as Console so existing questions in the README still make sense.
- [ ] README documents how to run the API (port, example `curl`) next to the Console instructions.

## Notes for implementers

- Workflow API: `BankingWorkflow.Create(...)` then `RunDetailedAsync(question, cancellationToken)`.
- Console packages to reuse: `Serilog`, `Serilog.Extensions.Logging`, `Serilog.Settings.Configuration`, `Serilog.Sinks.Console`. The API project will also need the ASP.NET Core web SDK.
- Do not register deposit/withdraw/transfer as LLM tools. `OperationTools` is only for `TransferExecutor`.
- Prerequisites unchanged: .NET 10, Ollama at `http://localhost:11434`, model `qwen2.5:1.5b-instruct`.
